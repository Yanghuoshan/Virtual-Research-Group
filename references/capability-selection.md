# Core Skill Selection: Worked Example

The routing authority is [the core skill](../SKILL.md). This document illustrates its policy; it is not another registry or an executable pipeline.

## Example: An Unexpected Graph Classification Gain

1. **Core diagnosis:** the gain may reflect source-related graphs crossing splits. Select `graph-evaluation` for a split audit, with graph/source IDs, the protocol and fixed output files. Choose the role/model explicitly.
2. **Specialist result:** the evaluator returns leakage findings and limitations. It does not change the global split, choose a model, or start a training run.
3. **Core decision:** accept or reject the audit. If the split is invalid, request a revised protocol and decide whether a new experiment is authorized. If the current skill collection lacks the required execution capability, report the gap instead of making the evaluator impersonate a trainer.
4. **Later core decision:** after verified results exist, assign one plotting task or one writing task. Neither is automatically inherited from the graph task.

## Distinguish Adjacent Responsibilities

- A single paper's identity or attributed claim calls for `citation-verification`; screening and synthesizing a bounded body of studies calls for `literature-review`. Neither authorizes an unbounded search.
- A proposed validation protocol calls for `experimental-design`; checking a specific graph/vision/control protocol calls for a matching evaluator. Drafting or auditing a protocol does not authorize executing it.
- Tracing claims through data, code, environment and artifact versions calls for `reproducibility-audit`; assessing a manuscript's argument and evidence calls for `manuscript-review`. Both return proposals, not core approval state.
- Generating and ranking multiple candidate hypotheses from evidence calls for `brainstorming-research-ideas`; reformulating one stuck representation, with structural analogy validation, calls for `creative-thinking-for-research`. The first returns a ranked candidate table with falsifiers; the second returns a reformulation memo with mappings. Both share laddering and analogy moves, so choose by the required artifact, not by the technique name.
- Auditing a language-model benchmark protocol calls for `llm-evaluation`; functional code results with pass@k, sandboxes and test oracles call for `code-model-evaluation`; claims about internal mechanisms call for `interpretability-validation`. Each audits supplied artifacts. None runs a benchmark, executes generated code, or trains/patches models; those are separate authorized execution tasks.

These distinctions are selection examples, not role bundles or phase requirements. Read the selected entry's full contract; only the core decides whether a separate follow-up task is needed.

## Selection Questions

- What exact uncertainty or artifact does the next assignment address?
- Does the candidate skill's input contract match available evidence?
- Which output will allow the core to judge success?
- What happens if a prerequisite is missing?
- Are requested tools already authorized and available?

Use the minimum applicable skill. Different tasks require separate core choices. No domain membership implies a bundle of tools. LLM-specific techniques remain possible specialist skills when actually relevant; the absence of a capability from this bundle is not a claim that it is scientifically irrelevant.
